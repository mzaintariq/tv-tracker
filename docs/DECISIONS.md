# Project Decisions

- Use Next.js with TypeScript.
- Use Supabase for authentication and database.
- Use TMDB for TV and movie metadata.
- Each family member has a separate account.
- Support Google login and email magic-link login.
- Prefer Google as the primary sign-in option; keep email magic-link as a secondary fallback.
- Google OAuth client secrets stay in the Supabase dashboard only; the app never stores or exposes them.
- Shared `media_items` metadata is readable by authenticated users but writable only via a server-only Supabase admin client using `SUPABASE_SECRET_KEY`; never expose that secret to the browser.
- Movie watch state uses `watched_at`: `NULL` means Watch Next (unwatched), non-`NULL` means Watched. Do not add a separate movie status column. Keep `is_favourite` as its own boolean.
- User-owned library tables reference `auth.users(id)` with `ON DELETE CASCADE`; do not add a second foreign key to `profiles`.
- Exclude Season 0 and specials from progress by default.
- Preserve original watched dates during TV Time import.
- Show all announced upcoming episodes.
- Group same-day season releases.
- Support light, dark and system themes.
- Track television episode-cache freshness separately in nullable `media_items.episodes_synced_at`; it advances only after every announced regular season has been fetched and its episode rows persisted. Season 0 does not affect this timestamp.
- Load Upcoming from cached rows first, then use a one-attempt client coordinator to refresh stale active non-ended shows with show concurrency two and re-render once.
- Treat episode metadata as stale after 24 hours. Recheck shared freshness in one batched read immediately before automatic synchronization.
- Reuse the Phase 4 ended interpretation (`tmdb_status` equal to `Ended`, case-insensitive). Ended shows are not refreshed automatically, so a revived ended series may require manual Refresh Metadata in Phase 6.
- Phase 6 retains full-season synchronization. Very long-running ongoing shows may generate more TMDB requests; incremental season synchronization is deferred.
- Movie removal deletes the `user_movies` membership row and therefore also deletes that movie's personal `watched_at` and `is_favourite` state. Shared `media_items` metadata remains cached. Unlike television episode history, movie history is not independently preserved, so removed movies no longer contribute to profile movie statistics.
- Phase 7 profile statistics are derived rather than stored. Television episode count and estimated time include all accessible `watched_episodes`, including history preserved after show removal; show-state counts and all movie statistics use current library memberships.
- Phase 8 uses a two-upload TV Time workflow: Analyze fingerprints and discards the ZIP; Apply requires the same ZIP and discards it again. Raw exports and irrelevant personal/security CSV rows are never persisted.
- TV Time legacy Unix `watch_date` values are authoritative; otherwise timezone-less `created_at` is interpreted as UTC and disclosed as an assumption.
- Multiple source events collapse to the latest source event. Existing TrackTV watched dates win and are never overwritten by default.
- TV Time active, non-archived shows may become active memberships. Removed, archived, and inactive shows import as history-only. Existing paused/dropped state and existing favourites are preserved; imported favourites are additive.
- Phase 8 retains the one-date watch-state model and does not add rewatch-event or separate removed-movie-history storage.
- Phase 8 matching is resumable with database leases. One confirmed TV show is applied transactionally only after every coordinate resolves or is explicitly skipped.
- Phase 9A exports an authenticated owner-only `tracktv.user-export` version 1 JSON document generated on demand and never retained. It includes portable profile preferences, current TV and movie memberships, provider IDs, favourites, tracking/watch state, original watched timestamps, and preserved television history for removed shows. It excludes account identity, internal UUIDs, import/mapping/diagnostic data, synchronization state, raw source metadata, and secrets. Removed shows carry history with only `tracking.inLibrary: false`; movies remain current-membership-only. Restore UI is deferred. The migration-free export is a best-effort request-time snapshot assembled from paged RLS-protected reads rather than one transactional database snapshot.
- Phase 9B standardizes global and installed-app branding on `TrackTV`. The App Router manifest uses original opaque standard, maskable, and Apple touch icons served from public `/icons/` paths, starts at `/shows`, and uses browser-native installation. TrackTV does not register a service worker, support offline tracking, or intentionally cache authenticated application data for offline use. The public manifest and icon assets bypass authentication processing; protected application routes remain protected.
- Phase 9C route failures use fixed, route-specific error copy with retry and optional safe navigation; arbitrary provider, database, and internal messages are never rendered. Successful empty reads remain empty states, failed reads reach an error boundary, and missing or RLS-inaccessible resources share non-disclosing not-found behavior.
- Phase 9C mutations return stable user-safe failures rather than raw Supabase, PostgREST, PostgreSQL, or provider messages. Client controls synchronously guard duplicate activation, clear pending state in `finally`, and refresh or navigate only after confirmed success; import upload responses preserve only allowlisted validation messages and otherwise use fixed fallback copy.
- Phase 9D uses one shared authenticated main landmark with a keyboard-visible skip link and a global `:focus-visible` baseline. Mobile safe areas are coordinated by `viewportFit: "cover"` and shared inset/navigation CSS variables so fixed bottom navigation and content clearance stay aligned. Natural browser focus remains the default; no automatic route-focus framework is introduced at this stage.
- Phase 9D uses native form controls and semantic fieldsets for related choices. Local failures use `role="alert"`, successful or non-critical updates use `role="status"`, static warnings remain ordinary text, and frequently polled progress panels announce only lifecycle changes rather than every count or percentage update.
- Phase 9D.3 corrects mobile and zoom reflow by shrinking flex/grid children with `min-w-0`, wrapping titles, using one-column media grids below 360px, stacking dense controls, fitting native inputs to their containers, and bounding detail posters. Global `overflow-x-hidden` is not used.
- Phase 9D.4 introduces `--control-border` for functional control boundaries (inputs, selects, secondary buttons, filters, and compact actions) without globally darkening decorative card borders. Prioritized interactive targets use a shared `touch-target` minimum of 2.75rem. Focus-visible uses a background outline plus foreground backup ring so accent controls remain distinguishable. Disabled controls stay at full opacity with muted or mixed colours rather than opacity-only fading.
- Phase 9E.1 splits Profile into `/profile` overview and `/profile/settings` account management. Statistics stream behind a Suspense boundary so the overview shell can paint without waiting for watched-history aggregation. Theme uses immediate client application with asynchronous persistence and rollback on failure. Browser tab branding uses TrackTV `app/icon.png` plus metadata icons instead of the default App Router favicon.
- Phase 9E.2 Watch Next includes only active incomplete shows that still have an unwatched released regular episode and either a regular watch or an unwatched regular air date within an inclusive rolling 30-day window from request time. Exactly 30 days ago counts as recent; Season 0/specials and future air dates never qualify. Active incomplete shows that miss that window appear only in Haven’t watched for a while, never also in Watch Next.
- Phase 9E.3 uses native season disclosures. Specials stay closed; the first regular season with an unwatched released episode opens, otherwise the regular season with the latest known released air date opens, with the first regular season as the deterministic fallback for future-only, unknown-date, or empty season data. Explore keeps its toolbar mounted and replaces only server-rendered result children with a localized pending skeleton during route transitions.
- The Phase 9E.3 Movies follow-up reuses the TV limited-section client with server-rendered movie-card children. Watch Next and Watched show 10 items initially while preserving their existing order and actions; Recently Watched and Favourites retain their existing behavior.
- Phase 9F.1 keeps compact library mutations on high-contrast poster overlays, collapses Recently Watched by default, and isolates intentional horizontal overflow to Profile favourite rails. Upcoming reuses the existing date-bounded RPC with a two-calendar-day lookback and anchors the initial viewport at Today without moving focus.
- Phase 9F.2 uses shared poster-surface and overlay-control classes for consistent hover, press, keyboard-focus, and reduced-motion feedback. Fine-pointer hover is capability-gated to avoid sticky touch hover; overlay actions remain sibling controls above poster links.
- Profile statistics use two concurrent owner-scoped, security-invoker RPCs: one typed scalar aggregate and one favourite-only poster projection. Profile no longer reuses the full Shows and Movies derivation pipelines because transferring complete memberships, episode metadata, and watched history was unnecessary for its scalar output. The RPCs preserve removed-show episode history, episode-runtime then show-average fallback, current-membership-only movie totals, released regular episode progress, active-only completed/caught-up classification, and case-insensitive `Ended` status. Application caching and a stored statistics table remain deferred because indexed request-time aggregation avoids invalidation and synchronization complexity; Shows and Movies remain separate performance-audit candidates.
- The Shows Watch List uses one authenticated, owner-scoped, security-invoker projection RPC instead of transferring every episode and watched-history row. It returns one scalar row per current membership, one next-episode projection where applicable, and at most 10 Recently Watched episode rows. Status precedence, released regular progress, case-insensitive ended classification, the inclusive 30-day Watch Next watch/air rule, timezone-derived caller dates, section ordering, and Watch Next/inactive exclusivity remain unchanged. No application cache, summary table, trigger, or stored aggregate is introduced. Upcoming and show detail retain their existing loaders. Secondary sections still receive all compact membership projections and construct their children before the client limiter reveals them; further RSC bounding is deferred to avoid broad UI/pagination changes.
- Release and streaming region is an explicit nullable owner preference stored separately from timezone as an uppercase ISO 3166-1 alpha-2 code. Existing users remain unset, and TrackTV never infers or persists a country from timezone. Future movie release, provider, and certification features must use the selected region and must disclose rather than silently apply any cross-region fallback.
- Regional movie release dates are shared TMDB metadata in `movie_release_dates`, never user-owned rows. A nullable `media_items.release_dates_synced_at` tracks this supplemental snapshot independently from core `last_synced_at`, matching the existing episode-freshness design without adding a sync-state table. The trusted movie synchronization path replaces the complete snapshot transactionally; supplemental failures preserve existing rows and freshness so adding a movie remains reliable.
- Movies Upcoming uses only the owner’s explicit profile region and profile timezone: region selects shared release rows, while timezone determines the current calendar date. It never infers a region or falls back across regions. Theatrical selects the earliest regional type 2 or 3 row and preserves the type; digital selects the earliest regional type 4 row. The general TMDB release date is never treated as regional theatrical metadata. Countdown wording is based on date-only calendar days. `Out Now` contains releases from today through 30 calendar days ago, newest first, unless the movie also has a future selected date; `Coming Soon` contains movies with a future selected date; `Dates not announced` contains movies with neither selected date. Older-only releases are omitted. Null region prompts for Settings. Cached results render first, then a one-attempt owner-verified coordinator refreshes snapshots older than 24 hours with concurrency two; supplemental failures preserve cached dates.
- The Movies Watch List page uses `media_items.release_date` only as a broad, non-regional library classification: unwatched movies after the profile-timezone calendar date appear in its limited `Upcoming` section, while released, today, and undated unwatched movies remain in `Watch Next`. This general date is never labelled or treated as a selected regional theatrical date; `/movies/upcoming` exclusively uses `profiles.region` and `movie_release_dates` for regional theatrical/digital tracking.
- Movies Upcoming tracks regional release availability rather than only unwatched viewing intent. Current watched and unwatched memberships may appear in Coming Soon or Out Now when a future or inclusive 30-day selected regional release is relevant; watched rows carry a subtle accessible badge. `Dates not announced` remains unwatched-only. Regionally dated movies qualify independently of their broad TMDB general date, preserving legitimate current regional re-releases of older catalogue titles. When both selected regional dates are missing, `media_items.release_date` is used only as an eligibility guard: null or at least `(profile-timezone today - interval '1 year')` remains in `Dates not announced`, while older general releases are omitted. It is never displayed or substituted as a regional theatrical date.
- Rich-media metadata uses one hybrid shared architecture. Core TV/movie synchronization persists only bounded stable projections on `media_items`: genres (20), vote average/count, original language, TV last-air date, TV networks (20), TV creators from `created_by` (10), TV origin countries (10), and movie production companies (20). Arrays contain only stable IDs/names or validated country codes; raw TMDB JSON, credits, providers, videos, and global certifications are never stored.
- Future detail extras remain server-only and public-metadata-only. TV uses aggregate credits because its roles summarize appearances across a series; movie credits provide top cast and up to 10 explicitly-jobbed directors. Top cast is limited to 10. Credits and TV ratings cache for 24 hours, videos for 12 hours, and regional providers for 6 hours, with request-local React cache deduplication. Provider and certification loaders require an explicit region and never infer from timezone or fall back across countries. Provider results retain TMDB/JustWatch attribution links.
- Preferred trailers accept YouTube only and rank Trailer type, official status, preferred language, then deterministic publication/provider order. External links derive from TMDB/validated IMDb identifiers; homepages must be credential-free HTTPS URLs. Optional loader failures use bounded categories and do not fail core detail data.
- The later rich-detail UI must initially show no more than 10 cast entries, request compact portraits at TMDB `w185` with tightly bounded `sizes`, consider small provider logos direct/unoptimized, use one bounded landscape backdrop contract, avoid original-size compact imagery, and add no YouTube thumbnails until an explicit image policy is approved. Detail UI, recommendations, and rich image consumers remain deferred.
- `media_items.rich_metadata_synced_at` independently records a successful core TMDB detail upsert using the bounded rich metadata mapper. Migration-era legacy rows remain null and therefore stale; empty genres, ratings, networks, or companies are valid fetched results and never act as freshness signals. Detail loaders lazily refresh null or seven-day-old shared metadata once and reload it in the same server request, while preserving usable cached details on failure. Less than seven full days is fresh; exactly seven days is stale. Manual show/movie refresh bypasses TMDB request caching and retains existing episode or regional-release reconciliation.
- Detail metadata refresh reuses one shared control for shows and movies: touch drag and desktop wheel overscroll can trigger only when their gesture begins at the document top. It ignores gestures started in horizontal scrollers, uses a 64px resisted threshold, prevents concurrent refreshes, preserves cached content, and respects reduced motion.
- Enriched Movie Detail remains one vertical route ordered as hero, tracking controls, overview, explicit-region releases, providers, cast/directors, trailer, production information, and trusted external links. The persisted shared row and regional release rows form the core shell. Four public-metadata loaders (providers, movie credits, preferred trailer, and external links/homepage) start in parallel and stream through independent Suspense sections; failures stay local. Existing endpoint caching remains 24 hours for credits, 12 hours for videos, 6 hours for providers, and the standard bounded detail cache for validated homepage links, with React request-local deduplication.
- Movie Detail renders text-only provider and cast projections, so enrichment adds no image consumers or optimizer transformations beyond the existing poster. Cast remains capped at 10. Provider availability retains JustWatch-via-TMDB attribution. Trailers are click-through YouTube links in a new tab with no iframe, autoplay, or thumbnail. Backdrops, recommendations, cast expansion, and person pages remain deferred.
- Movie Detail polish replaces the redundant library-status fact with at most two explicit-region release-state badges, while exact regional dates remain in Release Information. Its surface-backed tracking panel uses evenly distributed compact icon-only button targets with adjacent visible labels and `aria-pressed`; watched-date editing remains in that panel and follows the episode disclosure pattern, hidden until Edit. The destructive consequence stays in confirmation copy and compact help text.
- Movie and Show Detail omit the prominent manual metadata button and use the shared top-only touch-drag or desktop-wheel overscroll gesture for forced refresh. Keyboard users retain all tracking operations, automatic seven-day stale refresh, and route/section Retry recovery; no ordinary application task depends on forced refresh.
- Movie compact tracking actions and shared metadata refresh report success or general failure through the global notification drawer, avoiding duplicate inline status messages. Watched-date validation remains inline because it is field-specific and must stay programmatically associated with its input.
- Ratings audit found only the persisted IMDb identifier/link and TMDB score. There is no IMDb score, Rotten Tomatoes score, OMDb integration, approved ratings loader, ratings API key, or configured licensing/attribution contract. IMDb/Rotten Tomatoes scores remain deferred pending an explicitly approved provider; TrackTV does not scrape or derive them from TMDB.
